## 成品名讀法（2026-10-17 修 p1 225）
- 名稱框褐字米色底：`ocr.ps1 -Zooms 2,3,4,5 -Dark 0`（不二值化），**逐倍率各自拼行 snap、投票**（`dailyplan.vote_lines`）。舊版 `''.join(uikit.ocr(box, *shopkit.TITLE_OPTS))` 把 2 倍 / 3 倍結果串成一串（「成弓箭8口成弓箭8」）→ snap 全不過。
- 離線量測（`fixtures/daily_names_ocr.json`，p1 5 人 × 5 環 × 2 項真截圖）：舊讀法 3/50；新讀法 50/50 正確且全部「確定」、0 誤認。每格 OCR 約 1.4 秒（4 倍率一次呼叫）。
- 確定 = 有唯一得票名、沒有倍率投給別的名字，且（名字不含數字，或 ≥2 倍率同意）。數字尾碼單票 / 倍率間衝突 → 開快速合成彈窗讀大字 + 材料列（`peek_item` → `dailyplan.resolve_name`）：
  候選 = 兩邊得票名 + 同族只差數字的名（合成爪 1～10，配方材料各不相同），材料列唯一吻合的那個；材料列讀不到時只在面板與彈窗同名、或彈窗大字確定且面板沒投別名時接受；其他一律 225 不猜。
- 合成前核對（`craft_item` → `dailyplan.pop_check`）：見下節。

## 快速合成彈窗讀法（2026-10-17 第二輪，p1 樣本 `tools/.cache/daily-samples/pop-*.png` 99 張）
- 大字：框 380,398,204,50、`-Zooms 2,3,4,5 -Dark 0` 逐倍率投票（同面板）。99 張（含捲動版）全部讀對、0 誤認；舊框 392,404,180,38 是 97/99；**加寬但不加高**的框掉到 83～89（框邊雜訊），加高才穩。
- 材料列：整欄一張 OCR（`dailyplan.pop_rows`：只收 y 228～600、含中文的行，各倍率 y 差 ≤20 視為同一列逐倍率投票；「1000」數字行略過）→ 由上到下的列名。
  第一眼（剛開彈窗）50/50 完整讀對；▼ 亮 ⇔ 看不到「石幣」列（16 項，材料 4～5 種）。**▲ 亮時 y < 275 的行不收**（短清單被拖過，▲ 蓋住「有光澤的地瓜」只剩「有光澤的」→ 會 snap 成「有光澤的皮」）。
- `pop_mats`：看到石幣且 ▲ 沒亮 = 看完整張（complete）；▼ 亮就捲一次（`Tools.pop_scroll`）、第二張看到石幣後**依序合併**（重疊列只算一次）。15 項有捲動樣本：合併後全部完整吻合配方。
- `mats_fit`：full = 看完整張且名稱 + 順序和配方完全一樣；partial = 沒看全、讀到的是配方的依序子序列；看完整張卻不同（含讀漏一列）= 矛盾。
  **數量不從畫面讀**：紅字計數「0/1」Windows OCR 不二值化 / -Dark / -Light 都讀不到；item-book 裡「材料名單相同、數量不同」的配方 0 組 → 名單吻合 = 數量吻合。
- `pop_check(name)` → True / False / None：**一定要有大字證據**——item-book 有 38 組「材料完全相同」的不同成品（厚肉塊串燒 / 鹽味獸肉串燒、葉子烤蕃薯 / 半熟的芋頭、合成投擲斧頭 N / 合成斧頭 N、合成石 N / 合成迴旋標 N、合成兜 N / 合成鎧 N…）。
  大字有倍率投給同族（只差數字）以外的名 → False；材料矛盾 → False；大字沒讀到 → None；同族數字名 → 材料在同族唯一吻合才 True（大字數字讀錯以材料為準）；無數字名 → 大字得票 = name 且材料 full / partial → True。
  `craft_item`：None 且 ▼ 亮 → 捲一次再核對 → 捲回頂端（計數像素在頂端位置）→ 仍不是 True 就不合成 229。`peek_item` 只在 ▼ 亮且 `resolve_name` 還分不出時才捲。
- 離線結果（`fixtures/daily_pop_ocr.json`，OCR 原始行 + 人工答案，不存圖）：50 項 `resolve_name` / `pop_check` 全對、拿其他 39 個成品名核對 0 誤認；大字讀不到時 0 個 True。
  樣本注意：`pop-DKBO4-*`（04:58）畫面其實是 DKBO3 的清單（HP 687/100 相同，切角色沒切成）→ 只有 40 個不同成品；DKBO4 的真清單（合成爪 7 / 稍甜的燙青菜…）沒有彈窗樣本。
- **未實機**：捲動手勢只用樣本手勢、`pop_scroll` / 捲回頂端沒在腳本裡實跑過；捲回後計數像素位置靠「捲回頂端」假設。

## 流程（`daily.py run`）
`prep → read → plan → sam → mid → fish → final → finish`（細節與每段說明見 `tools/gui/daily.py` 檔頭）。
- 進度檔（每視窗各自）：全隊 `daily-team.json`（日期 / roles / stage / done[] / complete）、每人 `daily-<角色>.json`（`items` 10 項、`done` 已 1/1 綠、`rings[].crafted/submitted`、`bought{材料: 量}` 買到核對過才寫、`ledger{bag,personal,public}` 材料帳、`in_personal[] / in_public[]`）。
- **不讀背包 / 倉庫格數**（使用者 2026-10-17）：背包用「材料種類上限 13 種（`dailyplan.BAG_KINDS_MAX`，留 2 格放成品）」模型決定何時存個人倉庫（存最晚環才用到的種類）；個人倉庫滿才改存公共倉庫並記 `in_public[]`；實際背包比模型小（例：原本有雜物）→ 買不進（數量框沒歸 0）/ 取不出（bag rc 94）→ 再存一種後重試一次，仍失敗 227 / 228。
- **不讀石幣、不讀鑽石**（AGENTS §3-3 每日例外）：買到沒看數量框歸 0 +（每間店買完）背包名稱核對；合成後該項計數變綠；提交後獎勵計數 +1。
- 跨 00:00 → 220 停手；昨天沒跑完的進度檔今天不自動續跑（要 `--fresh`）；昨天跑完的今天自動新一輪。
- 公共倉庫是全隊共用：同名材料多人都存公倉時「整疊取」會取到別人的（個人倉庫滿的極端情況才發生，見報告風險）。
