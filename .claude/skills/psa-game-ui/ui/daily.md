## 成品名讀法（2026-10-17 修 p1 225）
- 名稱框褐字米色底：`ocr.ps1 -Zooms 2,3,4,5 -Dark 0`（不二值化），**逐倍率各自拼行 snap、投票**（`dailyplan.vote_lines`）。舊版 `''.join(uikit.ocr(box, *shopkit.TITLE_OPTS))` 把 2 倍 / 3 倍結果串成一串（「成弓箭8口成弓箭8」）→ snap 全不過。
- 離線量測（`fixtures/daily_names_ocr.json`，p1 5 人 × 5 環 × 2 項真截圖）：舊讀法 3/50；新讀法 50/50 正確且全部「確定」、0 誤認。每格 OCR 約 1.4 秒（4 倍率一次呼叫）。
- 確定 = 有唯一得票名、沒有倍率投給別的名字，且（名字不含數字，或 ≥2 倍率同意）。數字尾碼單票 / 倍率間衝突 → 開快速合成彈窗讀大字 + 材料列（`peek_item` → `dailyplan.resolve_name`）：
  候選 = 兩邊得票名 + 同族只差數字的名（合成爪 1～10，配方材料各不相同），材料列唯一吻合的那個；材料列讀不到時只在面板與彈窗同名、或彈窗大字確定且面板沒投別名時接受；其他一律 225 不猜。
- 合成前核對（`craft_item` → `dailyplan.pop_check`）：見下節。

## 流程（`daily.py run`）
`prep → read → plan → sam → mid → fish → final → finish`（細節與每段說明見 `tools/gui/daily.py` 檔頭）。
- 進度檔（每視窗各自）：全隊 `daily-team.json`（日期 / roles / stage / done[] / complete）、每人 `daily-<角色>.json`（`items` 10 項、`done` 已 1/1 綠、`rings[].crafted/submitted`、`bought{材料: 量}` 買到核對過才寫、`ledger{bag,personal,public}` 材料帳、`in_personal[] / in_public[]`）。
- **便利店店內購買順序 = 該店商品清單 index 由小到大**（2026-10-17 p1 兩次 227 修，`dailyplan.store_route` + `daily.buy_at` 防呆排序）：舊版「早環先買」讓清單靠前的商品排在後面買，`select_item` 只往下拖 → 已被捲出視野選不到（光滑的石 → 小枝 → 古代木 → 新木 → 球石 ✗；強的繩 → 皮的繩 → 薄的皮 ✗）。現在店內只往下捲、不回頭；`shopkit.select_item` 另加防呆：目標在視野上方 → `scroll_top` 往回拖到頂、drags 歸 0 再找（只重找一次）。存倉判斷（`make_room` / `choose_evict` 看 `_next_use`）與購買順序無關，不受影響；進度檔 bought 以名稱記，改順序不影響續跑、不會重買。
- **不讀背包 / 倉庫格數**（使用者 2026-10-17）：背包用「材料種類上限 13 種（`dailyplan.BAG_KINDS_MAX`，留 2 格放成品）」模型決定何時存個人倉庫（存最晚環才用到的種類）；個人倉庫滿才改存公共倉庫並記 `in_public[]`。**存倉順序與分批**（2026-10-17 修 p1 DKBO3 fish 227：mid 合成的 3 個成品 + 漁村前 4 家 8 種 + 米店 12 種 = 23 種，舊版成品不能存 → 無解）：`dailyplan.buy_batches` 每家店先排批——材料（最晚環才用的先）存完還不夠才存成品（最晚提交環的先；成品鍵 `成品:名` 在遊戲裡就用道具名存取）；還放不下 → 分批：買放得下的清單前綴 → 關店存倉（剛買、最晚才用的）→ 再進店買剩下的；連一種都放不下才 227（訊息寫背包帳種類 / 店種類 / 上限）。成品存倉後 mid 不提交該環（`products_away`），final `fetch_materials` 連成品一起取回再提交（離線測試，未實機）；實際背包比模型小（例：原本有雜物）→ 買不進（數量框沒歸 0）/ 取不出（bag rc 94）→ 再存一種後重試一次，仍失敗 227 / 228。
